# Build a Repository Explorer

Build a self-contained, dependency-light static explorer for the **current
repository** under `docs/repository-explorer/`. It has **two deliverables**:

1. **A Markdown documentation browser** — indexes every Markdown file (plus any
   canonical specs/configs you choose), with a folder tree, search, faithful
   GitHub-flavored rendering, rendered ```mermaid fences, and a per-heading /
   per-selection **review-commenting layer** (localStorage, export to JSON /
   copy-as-Markdown).
2. **A code-verified Architecture & Technology analysis** — produced by *reading
   the source*, published in two forms: a **Markdown** doc (browsable in the
   explorer, with mermaid diagrams) and an **expressive HTML page** with
   hand-authored **inline-SVG** vector diagrams (system topology, request flows,
   state machines). Every claim links to the file that backs it; doc↔code
   divergences are flagged honestly.

Read real files and cite them; never invent architecture, metadata, or
commentary. No runtime dependencies — the only third-party assets are the
vendored Markdown renderer and (optional) mermaid in the kit.

The engine is repo-agnostic; only **discovery config**, **branding**, and the
**authored analysis** are per-repo. The kit and the analysis playbook are bundled
in **this skill's own directory** (the folder containing this `SKILL.md`), under
`kit/` and `reference/`.

Locate that directory robustly — it works whether this runs as a plugin or as a
plain skill in `~/.claude/skills/`:
`${CLAUDE_SKILL_DIR}` is the skill's own directory in both modes (equivalently
`${CLAUDE_PLUGIN_ROOT}/skills/repository-explorer` when installed as a plugin); if
neither variable is set, fall back to the directory that contains this `SKILL.md`.
Then let:

- `SELF` = this skill's directory (as resolved above)
- `KIT  = SELF/kit`
- `REF  = SELF/reference`
- `DEST = <target repo>/docs/repository-explorer`

> **Golden rule:** the **mechanical manifest** (`manifest.json`, generated by
> `build_manifest.py`) and the **authored analysis** (the Markdown doc + the
> HTML pages) are separate; regenerating the manifest never clobbers the
> analysis. Treat `assets/*`, `serve.py`, `verify.cjs` as **copy-verbatim**;
> `build_manifest.py` and `index.html`'s `EXPLORER_CONFIG` as **adapt**; the
> analysis pages as **authored**.

## Phase 0 — Detect conventions

Before assuming anything, skim the tree, the READMEs, and the build/config to
learn what you're documenting. Record:

- **Where the docs live** — `README.md`, `docs/`, `CONTRIBUTING.md`, ADRs
  (`docs/adr/`), `CLAUDE.md`/`AGENTS.md`, design specs. Note big/canonical docs
  for the "Start here" list (`keyDocs`).
- **The repo's own honesty/status doc**, if any (e.g. a `HONEST-STATE.md`,
  `STATUS.md`, roadmap). This is the canonical shipped-vs-deferred source — find
  it and treat it as authoritative for status claims.
- **The services / entry points / dependency manifests** — `package.json`,
  `pyproject.toml`, `go.mod`, `Cargo.toml`, `docker-compose.yml`, Helm/Terraform,
  CI. These ground the technology-stack tables and the topology diagram.
- **Vendored / generated trees** to exclude from the browser (large forks,
  `node_modules`, build output) — these become `EXCLUDE_DIRS` /
  `EXCLUDE_PATH_PREFIXES` in `build_manifest.py`.

**Decide the review layer.** Default is on. If the user passed `--no-comments`
(or wants a pure read-only site), set `commenting: false`. **Decide scope:**
default is browse **+** full analysis; `--browse-only` stops after Phase 1.

## Phase 1 — Build the Markdown browser

1. Copy the kit into the target verbatim:
   `KIT/index.html`, `KIT/serve.py`, `KIT/verify.cjs`, `KIT/build_manifest.py`,
   and `KIT/assets/*` (`app.js`, `styles.css`, `marked.min.js`,
   `mermaid.min.js`) → `DEST/` (preserving `assets/`). If you are *certain* the
   repo has no mermaid and want a smaller footprint, you may omit
   `assets/mermaid.min.js` AND delete its `<script>` line in `index.html` — but
   `verify.cjs` asserts the two agree, so do both or neither.
2. **Adapt `DEST/build_manifest.py`** at its three `ADAPT` blocks:
   `INCLUDE_EXTRA_*` (canonical non-Markdown specs worth browsing),
   `EXCLUDE_DIRS`/`EXCLUDE_PATH_PREFIXES` (vendored/generated trees from Phase 0),
   and `CATEGORY_RULES` (map paths to the repo's vocabulary so the tree + the
   "Browse by area" grid read well). Run it; check the printed counts.
3. **Brand** — edit only the `window.EXPLORER_CONFIG` block in `DEST/index.html`:
   `brand`, `tagline`, optional `brandMark`/`accent`/`intro`, `commenting`,
   `keyDocs` (the curated "Start here" paths from Phase 0). Leave `analysisPages`
   empty for now (filled in Phase 3). Set `outputDir` if you used a non-default
   path.
4. Run `python3 DEST/build_manifest.py && node DEST/verify.cjs` and
   `python3 DEST/serve.py` to eyeball the browser. (If `--browse-only`, jump to
   Phase 5.)

## Phase 2 — Investigate the codebase (read `REF/ANALYSIS.md` first)

This is the part that makes the analysis *verified* rather than a restatement of
the docs. Follow `REF/ANALYSIS.md`. In short:

- **Fan out parallel sub-agents** — one per subsystem (e.g. one per service,
  package, or major directory). Each reads the real code and returns a structured
  report with **file:line evidence**: the tech stack, the request/data flow, the
  key modules, and explicitly *what is implemented vs stubbed*.
- **Read the dependency manifests yourself** — they are authoritative for the
  stack tables; don't take an agent's word for a version.
- **Cross-check the repo's own status/honesty doc** (Phase 0). When the prose and
  the code disagree, the code wins — and you note the divergence.
- Record a small evidence ledger (claim → file). Anything you can't ground, you
  don't print.

## Phase 3 — Author the analysis (both Markdown and HTML)

Produce the analysis in **two forms**, per the user's two needs ("MD" and
"expressive HTML with SVG; diagrams using MD rendered"):

1. **Markdown analysis** — write `<repo>/docs/ARCHITECTURE-ANALYSIS.md` (or fit
   the repo's docs convention). Prose + tables + **mermaid** diagrams for the
   quick structural views (the browser renders them). This lives in the repo and
   is picked up by the manifest automatically; add it to `keyDocs`.
2. **Expressive HTML** — copy `KIT/analysis/architecture.css` →
   `DEST/assets/architecture.css`, then author `DEST/architecture.html` from
   `KIT/analysis/architecture.template.html`. Use **hand-authored inline SVG**
   for the diagrams that deserve precision and theming (system topology, the real
   coded request pipeline, a state machine, a verification cascade). Source-file
   links open raw via `../../<path>`; Markdown-doc links open in the explorer via
   `index.html#/<path>`. Replace every `{{PLACEHOLDER}}`.
3. **Wire it up** — add each HTML page to `EXPLORER_CONFIG.analysisPages`
   (`{href,title,badge,sub}`) so it appears as a feature card on the home view.

Pick the right medium per diagram: **mermaid in the Markdown** for fast,
maintainable structural sketches; **hand-authored SVG in the HTML** when you want
exact layout, labelled boundaries, branch arrows, and theme-following vectors.
For a large codebase, fan out the authoring (one subsystem section per agent),
then assemble.

## Phase 4 — Verify (drive to zero failures)

```
python3 DEST/build_manifest.py     # -> manifest.json
node DEST/verify.cjs               # MUST exit 0
python3 DEST/serve.py              # eyeball in a browser
```

`verify.cjs` asserts: `app.js` initialises and exposes its hooks; the
slugify/resolvePath/markdown/mermaid-fence helpers behave; `manifest.json` is
well-formed with unique paths that all exist on disk; the kit assets are present
and the mermaid asset/script agree; and every `analysisPages` HTML file exists,
is tag-balanced, and its referenced local assets resolve. Also `node --check`
each JS file and `py_compile` the Python. Fix every failure. State honestly that
— without a headless browser — diagrams are validated **structurally**, not
pixel-checked; recommend `serve.py` to eyeball the SVG + mermaid.

## Phase 5 — Wrap up

Write/refresh `DEST/README.md`: how to serve, how to regenerate the manifest, and
the maintenance rules ("re-run `build_manifest.py` when docs change"; "when the
architecture moves, update `ARCHITECTURE-ANALYSIS.md` and `architecture.html` and
re-verify"). Report coverage counts and any doc↔code divergences you found.
Commit on a feature branch only if asked; do not open a PR unless explicitly
requested.

## Incremental updates & the doc-build changelog

After the first build, most re-runs are **updates**, not rebuilds. The Golden
rule already protects you: regenerating `manifest.json` never clobbers the
authored analysis. The `--update` mode extends that to the analysis itself, so
the Architecture & Technology pages track the code instead of going stale.

Anchor on the last build. Keep a **"## Doc build log"** section at the foot of
`ARCHITECTURE-ANALYSIS.md` (already indexed and in `keyDocs`), opening with a
machine-readable `built_from: <sha>` line followed by a newest-first, authored
changelog. An `--update` run:

1. Read `built_from`. If absent, do a full Phase 2–3 pass.
2. `git diff --name-only <built_from>..HEAD` (plus untracked) → the changed
   subsystems. Map them to the analysis sections, stack rows, and diagrams they
   back; print the mapping so the scope is auditable.
3. Re-run `build_manifest.py` (cheap, full), then re-author **only** the affected
   analysis sections and their SVG/mermaid diagrams, to the full Phase-3 bar.
   Leave the rest untouched. Re-run `verify.cjs`.
4. Set `built_from` to HEAD and prepend a changelog entry — date, commit range,
   and **what analysis changed and why**, authored from reading the diff, never a
   file-list dump.

This is the **documentation's** history, distinct from the repo's own product
`CHANGELOG.md` (which is browsed in the explorer, never edited here).

## Phase 6 — Evolve this skill

When a build surfaces a genuinely **reusable** improvement — an engine fix, a
sharper analysis rule, a recurring config or discovery need — write it back into
this skill's own directory (`SELF`) so the next invocation inherits it, rather
than letting it die in the target repo. Keep `KIT/` repo-agnostic (name no host
repo); fold better analysis patterns into `REF/ANALYSIS.md`. Run the kit's checks
(`node verify.cjs`, `node --check`, `py_compile`) green before and after, keep the
kit lean, and tell the user what you changed and why. Commit skill changes
separately from the target-repo work.

## Quality bar

Effort and judgement are the standard. Every user-facing string — stack rows,
diagram labels, status claims — must be specific to *this* repo and traceable to
a file; templated or "see the source" filler is a defect. The analysis must be
**verified against code**, not paraphrased from the docs, and must flag
divergences honestly (e.g. a stale LOC figure, a feature described as wired that
is only stubbed). Diagrams: prefer mermaid for quick structural sketches and
hand-authored SVG for the expressive set; both must follow the light/dark theme.
No new runtime dependencies. Works for repos with a handful or hundreds of docs.
